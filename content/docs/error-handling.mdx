# Error Handling

Every user-facing error produced by go-auth is returned as a **single-line, structured JSON body**:

```json
{"message":"Invalid credentials"}
```

`error` is never exposed. Neither is a stack trace, an internal error type, or any message that reveals the server's implementation to an unauthenticated caller.

The format is always the same: one object, one `message` key, a human-readable string safe to render in a UI. Errors are never paginated — a single failed login attempt produces one JSON object.

go-auth never uses `errors.Wrap`, `fmt.Errorf` with `%w`, or any other implicit wrapping on user-facing errors, so `errors.Is`/`errors.As` are never the right way to inspect them at the API boundary. Use the HTTP status and the `message` string together — the table below is exhaustive. If you do need to match programmatically in a test or integration, use the typed error constructors in `internal/errors`:

```go
// Rejected — hard-fail with status
internalerrors.ErrorConflict("session_limit_reached")

// informational (post-hook continuation) — no status
internalerrors.InfoConflict("session_limit_reached")
```

These create a typed error with a fixed `Code` and a category string (`"rejected"` or `"info"`) and implement a well-known interface for the handler layer. The HTTP layer maps categories to exactly two status families: `rejected` → `4xx`, `info` → `204`. The category is always just `"rejected"` or `"info"` — there are no other accepted values today.

## Response format

| Field | Required | Notes |
|---|---|---|
| `message` | Yes | Single-line, human-readable. Never includes sensitive data. |
| `code` | No | Machine-readable key — present only on some 4xx/5xx errors (e.g. `weak_password`, `otp_expired`, `admin_login_failed`). |
| `data` | No | Present only on `200 OK` success responses where a JSON body is structurally required (e.g. `{message, user}` or `{message, session}`). |
| `meta` | No | Present only on paginated list endpoints (`meta.total`). |

## The two-layer log structure

Every error produces two log lines, whether the response is a success or a failure:

- **At the route/handler level**: `msg="Auth handler returned an error" err="user_error_message"`. The `err` field is the user-facing message — safe for an external API. Any `reject`, `info`, or `4xx` errors from the response layer are excluded — they're expected outcomes, not failures.
- **At the service layer**: `msg="...", err="code"` with full context — user ID, the endpoint that failed, and the actual internal reason. The same goes for any successes that are genuinely noteworthy.

**`500 Internal Server Error`** logs a `level=ERROR`. Any other status logs `level=INFO`. A human looking at structured logs should find exactly one `ERROR`-level line for every 500; `INFO`-level lines for 4xx errors are expected and not actionable — only the handler-level error field is worth reading there.

## Error taxonomy

go-auth uses two kinds of errors at different layers of the stack. They surface at different layers, mean different things, and mix together in the same handler return statements.

### Service-layer errors

Returned by `internal/service/*` methods. When a service method returns an error, the handler layer routes it — it is never ignored.

- **`Errorf` errors** — the handler translates them to HTTP status and body right away. These are the 4xx/5xx errors: invalid credentials, password too weak, rate limited, and so on.
- **Typed info errors** — the handler keeps going through the rest of the request logic but eventually still returns the status that the typed error prescribed. These are the silent 204s: `AlreadyVerified`, `NewPasswordSame`, `SessionLimitReached`, `InvalidToken`. The HTTP body is never modified. Only one info error can be returned per request.
- **`nil` (no error)** — everything succeeded; the handler proceeds normally.

No error is a reserved sentinel that the handler silently checks with `errors.Is`. The routing happens through a category string on the error, not a global variable the handler imports and compares against.

Typed errors carry `kind` and `category` strings but no HTTP status; the handler is responsible for choosing the right status code based on the kind and category. Every user-facing error message is a hardcoded `Errorf(...)` string that the handler passes straight through to the `message` field — no translation or wrapping.

### Rejected / info errors

Returned by the response layer in `internal/feature/response`:

```go
response.Error(message, category, opts...) // or response.Errorf(...)
response.ErrorInternal(message)
response.ErrorNotFound(message)
response.ErrorForbidden(message)
response.ErrorTooManyRequests(message)
```

These are the two flavors of user-facing errors — they carry an HTTP status, a `message`, and optional extra fields (`code`, `data`). The handler layer handles both of them:

- `RejectedError` — ends the request immediately with `4xx` status.
- `InfoError` — posts the error onto the request context and keeps going through the rest of the request logic. The error middleware returns `204` if no earlier handler overwrites the HTTP response.

**`Errorf` only accepts `Errorf(kind, category, opts...)`** — it is *not* a `fmt.Errorf`-style format function. `InfoError` is only built by `Infof`; it is *not* a type to construct with `NewInfo(...)`. If you don't need to `errors.As` the returned error at the caller, both constructors are equivalent. Neither one adds stack traces.

### Endpoint-level errors

`Errorf` and `Infof` are used in response-layer endpoint methods, while endpoint-level errors are built with `Errorf` and `Infof`. These construct typed errors carrying a message, kind string, and error category (`rejected` or `info`); the HTTP status is not attached yet. Endpoint-level info errors are passed to the caller for the HTTP layer to decide the status. The handler routes these errors:

- Rejected → immediately sets the HTTP status to `4xx` or `5xx` and aborts.
- Info → attaches the error to the request context.
- Nil → no status is set; the handler keeps going.

The HTTP layer checks the context after calling a route handler. If it finds a `rejected` error, it sets the HTTP status to `400`, `403`, `404`, `409`, or `422`. If it finds an `info` error, it writes `204` if the handler didn't already write a response. If neither is present, it writes a `200 OK`.

The error messages in user-facing responses are always single strings — the `Errorf(...)` call and the `response.Error(...)` call each produce one message. These messages are never concatenated together, and the handler never joins multiple error messages into a single HTTP body. The body is always one JSON object with one `message` key.

## Error codes

Error codes are a recent addition and are **not yet present on all errors**. Many 4xx errors still produce only `message`; `code` is set only where explicitly noted below. All possible values are:

- `rate_limited`
- `weak_password`
- `invalid_csrf`
- `missing_csrf`
- `not_found`
- `invalid_token`
- `missing_token`
- `email_already_exists`
- `oauth_link_exists`
- `invalid_code`
- `expired`
- `password_update_conflict`
- `session_conflict`
- `admin_login_failed`
- `admin_login_blocked`
- `mailer_error`
- `internal_error`

<Callout type="warn" title="All mailer errors return 200 with `code: mailer_error`">
  Every `mailer_*` error from email delivery returns **200 OK** with `code: mailer_error`, not a 4xx or 5xx. The HTTP code reflects the user's experience — "Your password was reset" or "A verification code was sent" — not the mailer's failure. A successful signup, invite, password reset, password change, account deletion, or delete-request email that *arrives* is still a 200; the operator will notice the problem in server logs, where every outbound email is logged at `DEBUG` level with the recipient and message ID. The exception is the `POST /auth/mailer/test` endpoint, which always returns the SMTP status.

  The `POST /auth/admin/delete-user` endpoint is the sole exception to this rule. It runs an event hook and never sends email, so its error messages are returned directly, and `mailer_error` is not used there. A failed event hook returns `500 Internal Server Error` instead.
</Callout>
