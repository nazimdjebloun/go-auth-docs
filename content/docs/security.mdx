# Security

## The default is secure

Every security behavior in go-auth is **on by default**. There is no "enable security" step. CSRF protection, rate limiting, token rotation, and per-user session limits are active from the first request. No feature is documented as a security recommendation — they are all documented as defaults. You can weaken them, but weakening them is always a documented, opt-in deviation from the safe baseline.

Each security layer is independently documented, and each one clearly states whether it is a reference-page concern, a guide concern, or an implementation concern. Every security behavior has a documented failure mode and a documented log line. Every security error is both safe for the response body and logged for the operator. Every configuration option that changes the threat model is documented with its risk level, not just its API.

This security model is intentional. A developer who follows the defaults gets a secure system. A developer who wants to weaken security has to do so deliberately, knowing the risk, with a clear paper trail. There is no middle ground between "you are secure" and "you know you are not."

## Threat model

go-auth is a library that runs inside your process. It trusts your application to provide valid configuration, a working database connection, and a reasonably correct HTTP server. It does not trust any individual request — every request is validated independently, and no request is granted privileges based on its origin within the server.

| In scope | Out of scope |
|---|---|
| Credential storage, session management, CSRF protection, token rotation, email-based 2FA, admin user management | Application-specific authorization, infrastructure security, network security, DNS, TLS termination |
| Rate limiting for auth endpoints (built-in, not a replacement for infrastructure rate limiting) | Application-specific rate limiting |
| Audit logging for security-relevant events | Application-specific logging |
| OAuth login, registration, account linking, and unlinking | OAuth token management beyond login/registration |
| Organization management (multi-tenant) | Application-specific multi-tenancy |
| Admin user management with two-factor authentication | Application-specific admin functionality |
| Peer comparison and similar-username lockout | Application-specific user discovery prevention |

## Session security

Sessions are absolute, not sliding. A session that has exceeded its TTL is rejected on the next authenticated request, and the rejected request returns 401 — not 200 with the user's data, not 200 with a new token, and not a new session.

The library does not extend or reset sessions on every request. There is no rolling window, no session extension on activity, and no session renewal on login — the library was not designed to support those behaviors.

Session storage is the library's responsibility. The application stores sessions in its own database. The library never leaves stale sessions in the database — sessions are cleaned up on logout, on token expiry, on token rotation, and on a background sweep.

The library never returns the full session token to the client in a URL, a query parameter, or an error response. The session token is only stored in a cookie and returned once — at login or registration time — and is never re-sent to the client afterward.

## Passwords

### Password hashing and hasher migration

Every non-empty `password_hash` in the `users` table is produced by a single `port.Hasher.Hash` call, and that hash is what the `hasher` package keeps. Changing the hasher does not remove old verifiers from the database — old rows keep working. Every `Hasher` implementation is assumed to produce a format that self-identifies its algorithm. `New` rejects any hasher whose output cannot be self-identified — the library cannot verify a password if it does not know which verifier to use.

| Path | `Hash` call | Rehash-on-login | Notes |
|---|---|---|---|
| `POST /auth/register` | current hasher | — | `Users.Create` hashes once. |
| `POST /auth/register` (invite) | current hasher | — | `Users.CreateWithInvite` hashes once. |
| `POST /auth/login` | current hasher | guard: only when the stored cost is lower | Rehash replaces `password_hash` if the stored cost is lower. It is skipped when the stored cost is equal to or higher than the current hasher cost, so newer migrations do not trigger unnecessary rehashing of already-current hashes. |
| `POST /auth/reset-password` | current hasher | — | `Users.ResetPassword` hashes once. |
| `POST /auth/set-password` | current hasher | — | `Users.SetPassword` hashes once. |
| `POST /auth/admin/reset-user-password` | current hasher | — | `Users.AdminResetPassword` hashes once. |
| `PUT /auth/admin/users/:id/role` | no hash | — | Role changes do not touch the password. |

Every row retains its own algorithm metadata — `argon2id$...`, `$2a$...` — so a migration is a gradual roll forward, not a big bang. The hasher is called once per write, not repeatedly in loops. The library uses the password hash for both storage and verification; there is no separate comparison step. The hasher is the only component that touches password bytes — the handler, session layer, and admin endpoints never see a password in plaintext.

Every hash is also compared byte-for-byte. There is no prefix match, no partial comparison, and no regex against the stored hash. This is deliberate — the stored string is an opaque verifier, not a data structure the application should inspect.

**Argon2id is available but not the default.** The default is bcrypt with a cost factor of 12. Argon2id is available by selecting it in `WithPasswordHasher`. Its defaults — `Memory: 64 MiB`, `Time: 3`, `Threads: 4` — match the RFC 9106 section 4 memory-constrained recommendation. Argon2id's memory footprint is consumed per concurrent comparison, so benchmark and capacity-plan on the deployment hardware before enabling it.

Bcrypt input is measured in bytes, not characters. Multi-byte passphrases hit the 72-byte limit sooner than all-ASCII ones of the same apparent length. This is a `Validate` concern, not a `Hash` concern — go-auth checks password length before hashing, so a too-long password gets a clear `400 weak_password` instead of a generic `500` or silent truncation.

The cost factor is tunable. The default is a deliberate choice: bcrypt at cost 12. The library does not auto-tune it based on hardware benchmarks, and it does not time its own comparisons to choose a cost at startup. The cost is a config value, not a runtime measurement.

**Hasher selection is a long-term commitment.** The library retains old verifiers on the database — it does not rehash old passwords when the hasher changes. You cannot roll back an algorithm change if you later discover a problem with the new hasher. The cost and the algorithm are two separate things: the cost is a runtime value that affects the current hasher, but the algorithm is selected once and lives as long as the oldest row in the database.

If you set a high bcrypt cost on low-powered hardware, hashing becomes slow for every registration, login, and password change. The library does not protect you from that — the cost is your choice. Benchmark on your actual deployment hardware before increasing it.

### Secret rotation and the OTP pepper timestamp

The pepper timestamp governs only OTP/code expiry. Password peppering is independent.

For OTP codes, the HMAC pepper changes every time the root secret rotates. If you rotate the root secret but do not set a matching `PepperRotatedAt`, the library continues verifying against the new key, but a pre-rotation low-entropy code might be accepted if the rotation happened within the current `CodeTTL` window. `WithPepperRotatedAt` narrows that window: it tells the library the exact UTC moment the new secret went live, so any still-valid low-entropy code created before that moment is rejected as `expired` ("resend") instead of `invalid_code`.

Password peppering is separate. Each peppered row stores the version that was active when it was written, and that version maps to a specific key. The library never re-keys rows on read or on login — a row written with version 1 stays version 1 unless a password change or reset rewrites it with the current version. Password verification does not use `PepperRotatedAt` at all; it hashes with the stored version's key and compares byte-for-byte. The library never recomputes a legacy row against the current key — this prevents cross-version comparison errors and keeps the failure mode predictable: if the key is gone, the row is unverifiable, and the user must reset with a different recovery path.

**Lost pepper keys are unrecoverable.** If you remove a pepper version from the map while the database still contains rows at that version, those accounts are permanently locked out — there is no migration path, no fallback comparison, and no rehash-on-login that can recover them. The library refuses to start if it finds a stored version with no corresponding key, and its database ping and this query share a 10-second startup deadline, but the safety check only covers rows it can reach. If the key is deleted from the map after startup, the live process continues to hold it in memory and verifies successfully until it restarts — at which point it fails the same startup check.

**Lost pepper keys affect only peppered passwords.** If you never enabled password peppering, none of this applies. If you enabled it and later lost a key, the accounts written with that key are permanently locked, but their sessions are still valid until they expire. If you need to recover access for those accounts, you need a different recovery path — the library does not provide one.

### Verification code expiry

Code expiry is computed per code, not once per flow. A code sent before the rotation is checked against the old pepper, and a code sent after is checked against the new pepper — they use different derived keys. This means an old code fails as `expired` ("resend") before it reaches the comparison, even though its HMAC would otherwise succeed.

## 2FA login flow

1. Password succeeds → user is marked pending-2FA.
2. Library generates a short code, stores it, sends it by email.
3. `GET /auth/me` returns `pending_2fa` with a short TTL.
4. `POST /auth/2fa/verify` consumes the code → full session.
5. `GET /auth/me` returns `active` with user details.
6. `GET /auth/sessions` works immediately and lists only the new session.
7. `GET /auth/me` from the old (unauthenticated) session returns `pending_2fa`.

`GET /auth/me` has no special 2FA-awareness — it reads a flag on the session. It returns `pending_2fa` and a short TTL if the session is not fully authenticated, and `active` with user details if it is. It does not explain the full flow, and it is not the right place to look if you want to understand the login sequence — that's `POST /auth/login` and `POST /auth/2fa/verify`. `GET /auth/me` just reads the current state.

### How 2FA interacts with session limits

When `RequireEmail2FA` is true, the library limits 2FA sessions. Each failed 2FA attempt increments `two_factor_attempts`. Each expired code resets `two_factor_attempts` to zero and deletes the stale code, so the next generation starts at zero — this only matters when `RequireEmail2FA` is on. The maximum is `MaxFailedLogins` (default 3). Each successful 2FA check resets `two_factor_attempts` to zero, deletes the code, and sets `two_factor_enabled` to true. The login is counted — it creates a session — but the session is not fully authenticated until the code check succeeds.

The second `POST /auth/2fa/verify` succeeds and the session becomes fully authenticated. A third call with a valid code on a now-active session is a normal authenticated request.

`POST /auth/logout` during pending 2FA does not increment failed attempts.

### Admin login behavior

The `POST /auth/admin/login` route unconditionally requires a second factor when email 2FA is available, even if `RequireEmail2FA` is false. The code is always sent. Admin two-factor is disabled outside development by default. All invalid password or 2FA attempts on the same email address increment the same `failed_login_attempts` counter, and exceeding `MaxFailedLogins` locks the account — the lock is shared across login routes, and a 403 from admin login uses the same lockout event as a normal login. No other account is affected. The lockout expires after `LockoutDuration` (default 15 minutes).

### Suspicious 2FA attempt notifications

`POST /auth/2fa/verify` is a lightweight code check — it increments `two_factor_attempts`, expires old codes, and generates a new one on mismatch. `POST /auth/login` is a heavier operation: it hashes the password, manages sessions, and triggers an audit event. The two steps are cleanly separated: the password check belongs to `POST /auth/login`, and the 2FA check belongs to `POST /auth/2fa/verify`. An attacker who has the password still needs the email code.

After the 3rd wrong code on one account, the login event hook sends a *notify-only* `two_factor_suspicious` email — it does not block the attempt or interact with the 2FA code state, so it cannot delay or interfere with login. The suspicious email is sent in the same transaction as the login audit event, so the notification and the event are committed or rolled back together. The same email is never sent more than once per login session — `two_factor_attempts` resets to zero on a successful code, so the next login must fail three times again to trigger it.

## CSRF protection

The double-submit cookie is on in every deployment. `WithSecret` is mandatory at 32+ bytes, and `New` creates a `CSRFTokenConfig` with sensible defaults whenever you leave the field `nil` — so passing the struct overrides those defaults, it doesn't switch the layer on.

To actually turn it off, set `DisableCSRFToken: true`. That's intended for deployments with no browser clients — a CLI or a server-to-server API — where CSRF isn't in the threat model and the token round-trip buys nothing. Every state-changing route otherwise requires the client to `GET /auth/csrf-token` first and echo the cookie value back in the header.

### Where is your frontend?

The double-submit check needs the browser to **send** `_csrf` and let JavaScript **read** it so the value can be echoed in `X-CSRF-Token`. The deployment topology determines which configuration is required.

| Topology | Sends? | Readable? | What to set |
|---|---|---|---|
| Same origin, the frontend proxies the API (both reference apps do this) | yes | yes | nothing |
| Sibling subdomains, `app.example.com` and `api.example.com` | yes, they are the **same site** | not by default | `CookieDomain: ".example.com"` here, and leave `CookieConfig.Domain` alone |
| Different registrable domains, `panel.acme.com` and `api.example.com` | only with `SameSite=None` | **never** | `CookieSameSite: http.SameSiteNoneMode`, a secure cookie, and `ExposeCSRFTokenInBody: true` |

Two things that trip people up, both covered in full in the Deployment guide:

* **Subdomains are the same site, not a cross site deployment.** `SameSite` is computed from the registrable domain and ignores the subdomain and the port, so the default `Lax` cookie is sent normally there. Only *readability* is missing, and `CookieDomain` is what fixes it. A leading dot is optional: `net/http` strips it on write, RFC 6265 ignores it on read, and any `Domain` attribute covers subdomains.
* **Only the CSRF cookie needs a `Domain`.** Widening `CookieConfig.Domain` as well shares your session across every subdomain, and is not required for a sibling subdomain frontend to authenticate. Do it only when you want one login to cover both.

`CookieSameSite: None` means the browser sends the cookie on every cross-site request, including unauthenticated state-changing requests from `evil.com`. The double-submit check still compares `X-CSRF-Token` against `_csrf`, so `evil.com`'s JavaScript cannot read the cookie value. That comparison is the security boundary, not the cookie — the library enforces it on every state-changing route. The trade-off is that `SameSite=None` weakens the session's own defense against cross-site request forgery if `evil.com` happens to have a session token of its own. If you can avoid `SameSite=None`, do.

### ExposeCSRFTokenInBody

`GET /auth/csrf-token` returns `204 No Content` by default — no body, no token. The response is meant to set a cookie and nothing else.

`ExposeCSRFTokenInBody` makes it answer `200 {"token": "..."}` instead (with `Cache-Control: no-store`). Turn it on only for the third topology: across two registrable domains no cookie scope can make `_csrf` readable by the frontend, so the response body is the only channel left.

It does not weaken the check. The cookie is still set and still compared server side, and reading that body requires the caller's origin to be in `AllowedOrigins`, the same gate `OriginCheck` applies to every mutation. The exposure that matters in a cross site deployment comes from `SameSite=None`, which removes the browser's own barrier against the cookie riding along on a cross site request. This flag accompanies that decision rather than causing it, and it stays off by default because most deployments read the cookie perfectly well.

## Rate limiting

go-auth includes built-in rate limiting for all auth routes. It is enabled by default with sensible limits. The built-in rate limiter is not a replacement for infrastructure rate limiting — it is a defense-in-depth measure for auth endpoints only.

All configuration options live under `WithRateLimit` in the [Configuration](./configuration.mdx#withratelimit-and-its-narrower-variants--optional-on-by-default) page.

## Admin login

Admin two-factor is disabled outside development by default. Admin sessions are stored separately from user sessions. Admin session management is documented in the [Admin guide](./guides/admin.mdx).

The admin login flow is unconditional: even when `RequireEmail2FA` is false for normal users, `POST /auth/admin/login` sends a 2FA code if email 2FA is available. The code is always sent. The admin 2FA gate is on by default — disable it with `TwoFactorConfig.DisableAdminTwoFactor` only when you have another second factor in place.

The 403 from `POST /auth/admin/login` is not a new lockout type — it is the same `failed_login_attempts` counter as normal login. Exceeding `MaxFailedLogins` locks the account regardless of which route was used. No other account is affected.

## Peer comparison and similar-username lockout

Both are disabled by default. When enabled, peer comparison compares new user data against existing users' data and rejects requests with similar attributes. Similar-username lockout prevents accounts with similar usernames from being created.

## Cookie security

`Secure` is `true` by default unless `Environment` is `dev` and `BaseURL` is `http://`. See [Configuration → WithCookie](./configuration.mdx#withcookie--optional) for the full `SameSite`, `Domain`, and `Secure` resolution table.

## What the library does not do

go-auth does not:

- **Manage your HTTP server** — it provides a handler, not a server.
- **Set up CORS** — your application does this.
- **Manage your database schema** — it creates its own tables.
- **Handle deployment, TLS, or DNS** — your infrastructure does this.
- **Provide rate limiting beyond auth endpoints** — infrastructure rate limiting is your responsibility.
- **Encrypt data at rest** — your database does this.
- **Provide audit log retention** — the library stores events; retention is your responsibility.

## Keep the examples off the main branch

Every example in this documentation assumes a single-developer or proof-of-concept setup. Credentials are plaintext, middleware is minimal, and there is no HTTPS termination, reverse proxy, or build pipeline. Do not merge anything derived from these examples into a production branch without replacing every placeholder with a real secret, adding the middleware this documentation deliberately omits, and locking down the environment.
