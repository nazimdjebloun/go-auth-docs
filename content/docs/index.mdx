# go-auth

A drop-in Go library for email/password authentication, optional OAuth 2.1, and optional multi-tenant organizations, backed by SQLite or PostgreSQL — or both during migration.

**This is not a standalone service.** go-auth is a Go library that embeds directly into your application. You call `goauth.New`, mount the returned handler onto your HTTP server, and the library handles login, registration, CSRF protection, OAuth, sessions, and optionally organizations — all from inside your process. There is no sidecar, no separate binary, and no deployment topology to manage beyond your own service.

Your application controls how it starts, where it binds, which middleware surrounds the auth routes, and how it shuts down. go-auth provides the handler; your application provides the HTTP server.

For the most part you won't need to touch the database directly — the library handles setup, migrations, sessions, and most admin tasks. The routes and handlers expose what the library intentionally does not, typically because exposing it in the library would create a public API for something an application or platform should control: inviting new users, inviting users to organizations, and managing organization-wide settings and permissions. For the rest, the library already exposes complete programmatic APIs, and the routes are one layer above that — a thin HTTP mapping over what the application could do directly through `Auth` methods.

go-auth is a Go library, not a standalone app. It exposes Go APIs and an optional `net/http` handler. Use it directly in your Go application — there is no external deployment for the library itself. The separate `cmd/goauth` CLI is only for local development (scaffolding a new database) or one-time bootstrap (creating an initial admin user). It starts no servers.

```go
import "github.com/nazimdjebloun/go-auth"
```

go-auth provides two layers you can use:

- **`Auth`** — the full API: `Login`, `Register`, `RefreshSession`, `CreateOrganization`, and every other operation. It takes and returns plain values — no HTTP, no request parsing, no response writing. Use it from any Go code: tests, workers, CLIs, other handlers, anywhere.
- **`Handler`** — the optional HTTP layer. Mount it on a `*http.ServeMux` and it translates HTTP requests into `Auth` calls. It reads and writes JSON, but knows nothing about sessions, cookies, or middleware — those are your application's concerns.

Your application is responsible for setting up middleware, CORS, and the HTTP server itself.

## Feature overview

<Tabs items={['Authentication', 'Core infrastructure', 'Multi-tenancy & admin', 'OAuth 2.1']}>
  <Tab value="Authentication">
    Email/password authentication with optional peppered passwords, OTP-based two-factor authentication, email verification, and invite-only registration. The 2FA login code is always delivered by email. Peer comparison and similar-username lockout are built-in.
  </Tab>
  <Tab value="Core infrastructure">
    Token refresh, session management, CSRF double-submit, rate limiting, and a full audit-log sink. Audit writes are asynchronous, fire-and-forget, non-blocking, and never fail the request.
  </Tab>
  <Tab value="Multi-tenancy & admin">
    Organizations are optional. Admin users get a separate `/auth/admin/*` surface with its own session scope and a two-factor gate. Admin is disabled outside development by default.
  </Tab>
  <Tab value="OAuth 2.1">
    An optional provider layer for OAuth 2.1 login, registration, account linking, and unlinking. Built-in providers are stateless in production — no OAuth state is written to the database. Their HTTP handlers are one public surface the library does provide, but they remain optional.
  </Tab>
</Tabs>

## Two use cases

go-auth covers two distinct use cases, and most of the documentation separates them:

1. **Integrating go-auth into a Go service** — the primary use case. This is what the reference pages, guides, and most of the configuration documentation cover.
2. **Integrating a frontend or client with the go-auth API surface** — the second use case. This is covered in the [Client integration](./guides/client/index.mdx) guide.

## What go-auth does not do

go-auth does not provision your HTTP server, database, or schema. The only schema it interacts with is its own, and the only database operations it runs against the application schema are admin helpers (`ListUsers`, `DeleteUser`, `SetUserRole`) and the direct exports documented in the [Guides](./guides/authentication.mdx). It provides the handler; your application provides the server.

go-auth intentionally does not own migrations, environment configuration, startup orchestration, CORS, or logging — the application already has those, and owning them inside the library would make it unsuitable for most real-world services.

## Keep the examples off the main branch

Every example, sample config, and tutorial in this documentation assumes a single-developer or proof-of-concept setup. Credentials are plaintext, middleware is minimal, and there is no HTTPS termination, reverse proxy, or build pipeline. Do not merge anything derived from these examples into a production branch without replacing every placeholder with a real secret, adding the middleware this documentation deliberately omits, and locking down the environment — otherwise you're deploying a demo, not a service.
